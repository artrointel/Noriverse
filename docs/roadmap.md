# 개발 로드맵

2026년 11월 20일 기준. Phase 1에 착수했다. Phaser 오목과 충돌 장면, React의 화면·설정 관리, 로컬 Durable Object 방 서비스와 WebRTC 착수 동기화를 첫 프로토타입에 구현했다. 실제 Cloudflare 환경, TURN 중계와 모바일 실기기 매트릭스는 후속 검증 대상이다. 엔진과 인프라의 채택은 실측 후 결정한다.

첫 로컬 검증에서 Chrome 두 세션으로 방 참여, 양쪽 착수 동기화, DataChannel 종료 후 동일 보드 복구, 재경기를 확인했다. 테스트의 WebRTC 환경에서는 Chrome의 mDNS 후보 기능을 끈 상태에서 직접 연결에 성공했다. 기본 브라우저 설정, 실기기, 서로 다른 네트워크에서의 연결 성공률과 P95는 별도 측정한다.

사용자가 Chrome 두 창에서 로컬 프로토타입 동작을 확인했다. 이후 홈, 게임 라이브러리와 상세, 설정, 대기실, 경기·결과 화면을 연결했다. 오목의 로컬·친구 대전과 알까기 연습에 같은 설정·경기 화면 구조를 적용했다. 첫 방문에서 브라우저 언어 목록과 시스템 테마를 사용하며, 수동 설정은 브라우저에 저장한다.

오목·알까기에 목재 바둑판과 흑백 돌 이미지, 그림자와 물리 연출을 적용했다. 알까기는 연습과 함께 한 기기 2인 대전을 제공한다. 각자 다섯 돌을 들고 흑부터 한 번씩 튕기며, 돌의 중심이 판을 벗어나면 제거된다. 한쪽이 전멸하면 상대가 이기며 같은 샷에 양쪽이 전멸하면 무승부다. 한국기원 자료와 공개 게임의 조작·장외 규칙을 참고했다. [한국기원](https://m.baduk.or.kr/news/B02_view.asp?news_sum_no=18) · [다섯 돌 규칙](https://playfulo.com/ko/games/alkkagi) · [장외 판정](https://www.board-pan.com/guide-alkkagi.html)

배경음과 공용 UI·게임 효과음은 Web Audio 합성을 사용한다. 개인 설정은 언어, 테마, 사운드로 나뉘며 배경음과 효과음의 크기는 각각 저장한다. 오델로를 추가해 기존 오목 방의 착수 동기화, 기권과 재경기를 공유하도록 했다. 오델로는 돌을 뒤집을 수 있는 위치만 허용하고, 둘 곳이 없으면 패스하며, 양쪽 모두 둘 곳이 없을 때 점수를 확정한다. [오델로 공식 규칙](https://worldothello.org/about/about-othello/othello-rules/official-rules/english)

두 게임과 연습 종료에 마지막 장면을 유지하는 공통 결과 화면을 연결했다. 이름을 등록한 사용자는 익명 세션 쿠키로 프로필을 사용한다. 종료와 기권 기록은 프로필별 Durable Object에 경기 ID로 중복 없이 저장한다. 기존 게임 기록의 시간도 합산하며 1레벨에서 시작해 3,600초마다 레벨이 오른다. 공유 링크에서 누적 시간, 게임별 합계와 각 게임의 최근 기록 20개를 조회한다. 전적은 브라우저가 제출하며, 한 기기 대전은 흑 기준으로 기록한다. 오목은 방마다 3–3 허용 또는 흑 착수 금지를 선택할 수 있다. 판정은 한 수에서 열린 삼을 만드는 두 방향을 확인하며 5목 승리가 우선한다. [3–3 규칙 참고](https://www.renju.net/rifrules/)

| 단계 | 주요 작업과 완료 기준 |
| --- | --- |
| Phase 0 · 기획과 설계 | 벤치마킹, 요구사항과 위험, 엔진·네트워크·UI 등 후보 설계와 검증 지표를 문서화했다. Phase 1의 범위와 검증 조건을 합의했다. |
| Phase 1 · 기술 타당성 | 최소 보드와 원형 충돌 장면으로 React와 엔진, WebRTC와 방 코드, 모바일 입력·회전·최대화면, 상태 동기화, 설정 변경을 검증한다. 실측에 근거해 엔진과 인프라를 선택한다. |
| Phase 2 · 플랫폼 기반 | 카탈로그, 등록과 지연 로딩, 파티·경기 생명주기, 공통 로비와 게임 셸, 테마·번역·화면 관리, 연결 복구를 만든다. 같은 로비에서 새 경기를 시작하고 환경 설정을 바꿔도 현재 경기가 유지되어야 한다. |
| Phase 3 · 초기 게임 | 자유룰 오목과 단순화한 알까기를 후보로 구현한다. 두 번째 게임은 공통 런타임을 복제하지 않고 등록, 게임별 설정, 규칙과 Scene을 추가해 동작해야 한다. 같은 방에서 두 게임 간 전환을 검증한다. |
| Phase 4 · 출시 준비 | 모바일 접근성·실기기 호환성, 장애 대응, 인프라 한도, 사용성, 성능을 개선한다. 실제 친구 그룹으로 검증하고 릴리스·롤백과 지표 수집 경로를 준비한 뒤 공개 여부를 결정한다. |
| Phase 5 · 콘텐츠 확장 | 공통 기능에서 확인된 재사용 요구를 반영하고 게임을 추가한다. |
| Phase 6 · 장기 기능 | 사용 지표를 근거로 공개방·매칭, 선택적 계정·프로필 및 성장 기능을 검토한다. |

## MVP 제안

공개 MVP는 **두 사람이 방 하나에서 오목과 알까기를 오가며 플레이**하는 범위를 권한다. 둘 다 익숙한 규칙이고, 턴제 상태와 물리 상태의 차이로 공통 계층을 검증할 수 있다. 내부 테스트는 오목 한 종으로 시작하고, 알까기는 물리와 입력 최소 기능부터 구현한다. 출시 일정이나 검증 결과에 따라 한 종만 공개하고 두 번째 게임은 내부 검증에 쓰는 대안도 있다. 그 경우 게임 전환에 대한 사용자 가설은 두 번째 게임 공개 뒤 확인한다.

- 게임 라이브러리와 상세·규칙, 익명 닉네임, 1:1 사설 방, 링크 또는 코드 참가, 최소 대기 로비, 플레이, 결과, 재경기, 같은 방의 게임 전환
- 신뢰성 있는 턴제 동기화와 호스트 물리 상태 전달, TURN, 단기 재접속과 스냅샷 복구, 호스트 이탈 안내
- 한국어·영어, 라이트·다크·시스템 테마, PC와 모바일 입력, 양방향 레이아웃 및 페이지 내 확장과 지원되는 환경의 네이티브 최대화면
- 기본 접근성, 오류 원인 안내, 운영용 연결·비용 지표

싱글플레이와 AI, 공개방·계정·순위표, 채팅, 큰 파티·팀, 비공개 정보 게임, 장기 세션 저장과 호스트 이전은 초기 공개 범위에서 제외한다. 추후 수용을 위해 구조적 경계만 확보한다.

## Phase 1 검증 범위와 기준

Phaser 4.2.1과 Cloudflare 방 인프라·STUN/TURN을 첫 후보로 검증한다. 오목 보드로 방 참가·착수·상태 복구를, 작은 원형 충돌 장면으로 물리·렌더링·터치 입력을 검증한다. 아래 수치는 합의한 초기 목표이며 표본 수와 기기·네트워크별 결과를 함께 기록한다.

| 검증 | 방법과 초기 목표 |
| --- | --- |
| 초대 및 P2P | PC Chrome·Edge·Firefox와 macOS Safari, iPhone Safari, Android Chrome 중 실제 접속 쌍을 정한다. 동일 Wi-Fi, Wi-Fi ↔ LTE/5G, 상이한 인터넷 회선 및 가능하면 제한망, 강제 TURN/TLS를 포함한다. 여러 네트워크에서 적어도 60회 유효 방 참가를 시도해 성공률 목표는 95% 이상, 사용자가 참가를 누른 뒤 플레이 가능까지 P95 8초 이내다. 네트워크·기기별 표본 수와 직접·중계를 별도 보고한다. |
| 신호와 복구 | 정상·만료·정원 초과·버전 불일치, 손님 백그라운드/네트워크 전환, 호스트 백그라운드/종료, 중복 입력과 연결 재시도를 검증한다. 단절 전후 마지막 확정 상태가 일치하고, 호스트 장기 이탈은 유예 후 중단 처리되어야 한다. |
| 엔진 통합 | 같은 크기·리소스의 장면에서 Phaser 4.2.1을 우선 측정해 필요 시 3.90 또는 Excalibur와 비교한다. 초기 카탈로그에는 엔진 요청이 없어야 한다. 중급 모바일과 정한 네트워크 조건에서 캐시 없는 게임 진입 P95 3초 이내, 물리 장면 30 FPS 이상을 목표로 하고 압축 바이트, P95 프레임 시간과 반복 게임 전환 후 메모리 추세도 기록한다. |
| 모바일과 접근성 | 세로·가로에서 회전, 브라우저 주소창 변화, 최대화면 시작·복귀와 인앱 브라우저의 지원 제약을 확인한다. 클릭·터치 좌표와 보드가 일치하고, 화면 모드가 바뀌어도 진행 상태가 유지되어야 한다. 키보드와 화면 낭독 흐름을 핵심 화면에서 확인한다. |
| 테마와 언어 | 두 참가자의 언어를 서로 다르게 설정하고, 동시에 진행 중인 경기에서 테마·언어를 바꾼다. React와 엔진의 표시 변경, 지속 저장, 경기 ID와 보드 상태 유지, 상대 언어에 영향이 없는지 검증한다. |
| 비용과 서비스성 | 검증 비용은 무료 이용 한도 내에서 최소화한다. 반복 검증은 로컬에서 우선하고 배포 환경은 서로 다른 실제 네트워크와 강제 TURN 검증에 사용한다. 방 생성·신호·재접속 요청량과 TURN 발신량을 추적하고, 기존 프로젝트와 계정의 한도를 공유한다면 합산 사용량을 확인한다. 한도에 근접하면 추가 사용을 멈추고 검증 범위를 조정한다. |

## 합의할 주요 사항

| 시점 | 결정 |
| --- | --- |
| Phase 1 준비 | 합의한 기준에 따라 실제 테스트 기기·네트워크 조합을 기록한다. 배포 환경이 필요한 시점에 사용할 Cloudflare 계정의 가용 한도와 접근 범위를 확인한다. |
| Phase 1 종료 | 실측을 바탕으로 엔진·인프라·호환 브라우저 범위, 연결·모바일·로딩 기준, 초기 배포 방식을 채택한다. |
| Phase 2 시작 전 | 방 코드·초대 TTL, 자리 유지와 호스트 유예 시간, 방 잠금과 손님 제거 정책, 인앱 브라우저 지원 범위, 오류 지표 보존 기간을 정한다. |
| Phase 3 시작 전 | MVP 게임 두 종과 세부 규칙, 둘째 게임의 공개 여부, 디자인과 브랜드 방향 및 접근성 목표를 결정한다. |
| 공개 전 | 도메인과 운영 예산, 개인정보 처리 범위와 보관 기간, 콘텐츠·자산 권리, 출시 여부를 결정한다. |
